# Epic 10 — organization requirements audit

[Epic 10 — Organizations CRUD](https://github.com/JohnnyCPP/42_transcendence/issues/80) · [Story 10.1 — Audit](https://github.com/JohnnyCPP/42_transcendence/issues/81)

This audit reflects the application at commit `be9c663` on the local `pablgarc` branch, which includes `origin/main` at `a225d32`. The interface calls an organization a **workspace**. **Present** means the requirement is implemented, **Partial** means a gap remains, and **Missing** means the requirement has no implementation.

| Requirement | Status | Current implementation and gaps |
| --- | --- | --- |
| Create an organization | Present | The workspace form calls authenticated `POST /api/v1/organizations`. PostgreSQL creates the organization and its owner membership in one transaction. The endpoint returns **201 Created** with `{ organization }` and the caller's `owner` role. The handler, generated OpenAPI schema and integration tests agree. |
| Edit an organization | Present | Owners and admins can update the name and slug in workspace settings. `PATCH /api/v1/organizations/:id` returns **200 OK** and also supports an optional description of up to 5,000 characters, with `null` to clear it. Description editing is available through the API. The UI updates the active workspace and list after a successful save and preserves the caller's role. |
| Delete an organization | Present | Owners can archive a workspace after confirming. The backend soft-deletes it and excludes it from the list and detail endpoints. Archiving the last workspace leaves an empty list with an explicit creation form, including after reload. |
| Add a user to an organization | Present | Owners and admins add an existing active user by `username` through `POST /api/v1/organizations/:id/members`. The role defaults to `member`, and only owners can assign `admin`. Missing or inactive users return 404. Duplicate memberships return 409 with `ORGANIZATION_MEMBER_EXISTS`. |
| Remove a user from an organization | Present | Owners and admins can remove eligible members from workspace settings after confirming. PostgreSQL removes the user's board memberships in that organization in the same transaction. A missing membership returns 404. The UI explains that the owner cannot be removed or demoted, and the API enforces this with 403 and `ORGANIZATION_OWNER_IMMUTABLE`. |
| View organizations (list) | Partial | The authenticated list endpoint returns the caller's non-archived organizations, and the workspace selector shows the first page. The API defaults to 50 results, and the selector has no controls for loading later pages. |
| View one organization (detail) | Present | `GET /api/v1/organizations/:id` requires membership and returns 404 for archived or inaccessible organizations. The active workspace settings show its name, members, roles and actions available to the viewer. |
| Create, read and update within an organization | Present | Owners and admins can create boards in their organization, and members can list and read its boards. Board updates respect the effective board role. Lists and cards also enforce board access, including write restrictions for observers. |

## Permissions and verification

- All organization routes require a session. The routes under `/organizations/:id`, including organization board routes, apply the shared organization role guard. The tests exercise 401 for missing sessions, 404 for callers outside the organization and 403 when a member lacks the required role. The existing membership PUT supports adding or updating by user ID and allows an admin to assign or repeat a `member` role within the service's rules. Only owners can grant or change admin roles. [Organization routes](../../src/modules/organizations/organizations.routes.ts) · [Organization service](../../src/modules/organizations/organizations.service.ts) · [Shared guard](../../src/modules/authorization/requireScopeRole.ts)
- The integration suite was rerun for this audit. Nine tests passed and one API-key test was already marked as skipped. The organization tests check creation with 201, update with 200, validation and archiving. The RBAC tests check membership conflicts, concurrent additions, owner protection and scoped permissions. The three PostgreSQL RBAC tests also passed during validation of this commit. [Organization integration tests](../../test/integration/organizations.routes.test.ts) · [In-memory RBAC tests](../../test/integration/rbac.routes.test.ts) · [PostgreSQL RBAC tests](../../test/integration/rbac.postgres.test.ts)
- The earlier Chrome check on this commit used two sessions and verified explicit creation, saving settings, adding a member by username, read-only settings for the member, archiving the last workspace and seeing the empty list after reload.
